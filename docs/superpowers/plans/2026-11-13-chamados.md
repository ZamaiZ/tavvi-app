# Chamados por mesa Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use `superpowers:executing-plans` natively, task by task. The project explicitly prohibits adding or running tests; use static review checkpoints instead. No Git commands may be run.

**Goal:** Add table service calls with public mesa context, staff claim/resolve workflow, Supabase Broadcast realtime, pending counters, sound, and complete UI states.

**Architecture:** An additive Supabase migration owns idempotency, membership checks, statuses, and trigger Broadcasts. Next Server Functions wrap public and member RPCs; shared public profile components render identifier context while the panel shell owns one restaurant-scoped realtime subscription and count.

**Tech Stack:** Next.js 16.4.2 App Router, React 19, TypeScript, Supabase JS 2.118, PostgreSQL functions/triggers, Zod 4, `motion/react`, existing shadcn components.

**Spec:** `docs/superpowers/specs/2026-11-13-chamados-design.md`

## Global Constraints

- “Do not run Git commands, typecheck, build, lint, or test commands.”
- “Do not add or run tests.”
- Use only the current Supabase URL and publishable key; add no dependency, secret, or external rate-limit service.
- Add an incremental migration; do not edit a clean-install baseline.
- Public menu/call status must not create an authenticated user session or grant direct table access.
- Read local Next 16.4.2 docs before changing App Router code; route `params` are promises and `error.tsx` receives `retry`.
- Use any active membership in the current restaurant for staff actions; `memberships.position` does not authorize.
- Use token-bound Realtime Broadcast policies; do not add `service_calls` to `supabase_realtime` publication.

## Review Focus

1. Invalid/inactive token or unpublished menu cannot show table number or request/status data — migration resolver and public route.
2. Repeated/concurrent requests cannot create two open calls; return an existing call before hourly throttling — SQL `request_service_call` and unique index.
3. Concurrent staff claims have one winner, and cross-restaurant users cannot claim or conclude — SQL functions, RLS and server action context checks.
4. Guest status events cannot leak to another token; staff broadcasts require active membership — Realtime policies and triggers.
5. A live call cannot be detached from its mesa by changing the tag table number — SQL identifier update RPC and mapped panel error.

Automated validation for these cases is deliberately omitted because the repository forbids adding or running tests. Each task ends with static review of its SQL/types/authorization paths.

## Interfaces

- `PublicTagContext = { token: string; tableNumber: number }` is passed from `/t/[token]` through `RestaurantPublicProfile` to `PublicServiceCall`.
- `PublicServiceCallDTO = { callId: string; tableNumber: number; status: "pending" | "in_progress" | "resolved" }`.
- `getPublicServiceCallStatusAction({ token })` returns `{ ok: true, data: PublicServiceCallDTO | null }` or a failure code.
- `requestServiceCallAction({ token })` returns the existing/new call including `created`.
- `PanelServiceCallDTO = { id, restaurantId, tagId, tableNumber, status, createdAt, claimedAt, claimedBy, resolvedAt, resolvedBy }`.
- `getPanelPendingServiceCallsCountAction({ expectedRestaurantId })`, `claimServiceCallAction({ expectedRestaurantId, callId })`, and `resolveServiceCallAction({ expectedRestaurantId, callId })` verify the active panel restaurant and rely on SQL membership checks. The active call list is read in the authenticated route Server Component under RLS.
- Staff topic is `service_calls:{restaurantId}`; guest topic is `service_calls_guest:{token}`. Guest event is `service_call_status` with `{ callId, status }`.
